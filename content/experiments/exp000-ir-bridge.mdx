## Why

Before the arms arrive, prove the harness end to end on hardware that costs nothing:
command in, safety gate, device, observed outcome, all in one event log.

## Devices

The RM4 Mini only hears infrared, so the first job was finding out which remotes are IR.
A toy robot's two-button remote is. The ceiling fan's remote and a second robot remote are
radio, and the smart TV remote is Bluetooth, though the TV itself still obeys standard IR
codes. The toy robot became the experiment's device, and later Experiment 1's robot.

## Protocol

1. Learn IR codes for each device.
2. Send each command 10 times through the tool registry. Record the outcome by eye.
3. Run the same script as a null test with sending disabled.
4. Replay run 1 from its log and compare.

<Callout>Fireplace is excluded from automated trials. Manual, supervised commands only.</Callout>

## Bench notes

The first hardware session (see the log) turned up two things worth a decision record:
holding a robot button has to be played by the blaster, not timed over Wi-Fi, and a learned
code has to be trimmed to one clean frame or it can outlast the safety cap.

## Results

The harness works end to end on real hardware. The robot drives from the command line
and from this site's admin page: the page only queues a request, and the lab machine's
safety gate decides. Every request, decision, send and outcome is in the event log.

The first moves came out as jerky surges, and the cause was Wi-Fi latency between
per-frame sends. Timed moves are now played by the blaster itself, from one clean frame
with a repeat count. That made the motion smooth and closed a gap where a long recorded
code could outlast the gate's 3 second cap (ADR 0008).

The formal 10-trial counts and the null test weren't run as published runs: the bench
sessions mixed tuning with real commands. The camera judge in Experiment 1 replaced the
person typing y or n.
